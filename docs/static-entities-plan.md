# `docs/static-entities-plan.md`

## Summary

Introduce authored static entities as first-class map content with three distinct record types:

- `asset version` for uploaded source assets plus normalized runtime artifacts
- `archetype` for stable, globally reusable placeable content definitions
- `static entity` for per-map placements of archetypes

The API server is the source of truth for:

- asset metadata
- asset binaries
- asset processing status
- archetype catalog data
- static entity persistence

The first milestone is limited to single-anchor props only:

- buildings
- landmarks
- industrial props
- natural props

Bridges, walls, roads, docks, and other span-authored assets are explicitly out of scope for v1.

## Core Decisions

### Placement Model

V1 static entities are single-anchor props with:

- human-readable entity ID unique within a map
- optional display label, autogenerated by default from archetype + ID
- `archetypeId`
- anchor position `{ x, z }`
- live terrain-snapped vertical placement
- always-available `yOffset`
- free yaw
- uniform scale only
- lifecycle state `active | disabled`

Entity identity represents the authored placement on the map. Changing the archetype of a placement keeps the same entity ID.

### Grounding And Validity

Entity Y is not primarily authored as an absolute coordinate.

For each placement:

- effective Y is derived from terrain in real time
- grounding is footprint-aware
- footprint shape is an oriented rectangle
- grounding samples center + four corners of the rotated footprint
- grounding height is the average of those samples
- validity is checked using max height delta across the sample set
- `yOffset` is applied after grounding

Invalid placement is derived, not persisted. Invalid placements are allowed:

- after terrain changes
- after explicit archetype changes

In v1, invalid placement only produces editor warnings. It does not auto-disable entities and does not block publish/export flows.

### Collision

Collision shape for v1 building-style assets is an oriented box matching the footprint orientation.

Collision policy is asset-version-owned, not placement-owned. Asset versions define collision class as part of their derived runtime metadata.

### Content Ownership

Geometry, collision, and grounding metadata live on the asset version, not on the archetype.

That includes:

- normalized GLB binary
- derived oriented footprint dimensions
- derived oriented collision box dimensions
- collision class
- grounding policy
- max height delta threshold
- instancing eligibility

Archetypes are still required as stable content identities. They are not code constants in `packages/contracts`. They are DB-authored global records with:

- globally unique human-readable stable slug
- display name
- controlled category
- free-form organizational tags
- immutable binding to exactly one asset version
- lifecycle state `active | deprecated | archived`

An asset version may exist unbound, but once bound it may be used by exactly one archetype.

### Asset Pipeline

Asset ingestion is admin-driven and API-owned.

V1 asset flow:

1. upload original asset through admin
2. API stores original file
3. API runs server-side normalization pipeline
4. API produces normalized GLB runtime artifact
5. API auto-derives candidate footprint/collision/grounding metadata
6. admin reviews derived metadata in preview tooling
7. asset version is manually approved in v1 and becomes `ready`
8. ready asset version may be bound to a new archetype

Asset version lifecycle:

- `uploaded`
- `processing`
- `review`
- `ready`
- `failed`
- archived/soft-deleted

Rules:

- original + normalized files are both stored
- clients only consume normalized binaries
- normalized binaries are immutable by `assetVersionId`
- failed asset versions remain visible with diagnostics
- failed asset versions cannot be bound
- ready asset versions are immutable; corrections require a new asset version

### Rendering

Gameplay and admin both resolve placements through archetypes, but asset binaries come from the API.

Lookup chain:

1. chunk data returns static entities with `archetypeId`
2. client/admin fetch archetype catalog data from API
3. archetype resolves to bound `assetVersionId`
4. normalized GLB is lazy-fetched by `assetVersionId`

Catalog scope:

- gameplay uses a referenced-subset archetype catalog
- admin uses global catalog plus referenced subset for the current map

Rendering strategy for v1 is hybrid:

- baseline support for cloning loaded scene graphs
- optional instancing for asset versions that are automatically marked instancable
- manual override allowed during review

### Editor

The existing map editor remains 2D-first.

Entity authoring uses:

- mixed interaction model
- toolbar mode for entity placement/editing
- sidebar catalog for selecting the active archetype
- click-to-place workflow
- on-canvas oriented footprint overlay
- anchor marker
- facing indicator
- rotate handle
- numeric inspector controls

Movement behavior:

- free movement by default
- modifier-based snapping
- snapping targets: tile grid + metre increment

Selection behavior:

- multi-select supported
- bulk operations: move, state, scale
- no bulk archetype swap in v1
- duplication supported for single and multi-selection
- duplication creates new IDs and labels with a fixed world-space offset

Outliner/list behavior:

- map-wide auxiliary entity list
- search by entity ID, display label, and archetype name
- filter by archetype/category
- jump to entity

### Persistence And Read Model

Static entities participate in the shared map revision stream.

Mutation model:

- simple CRUD only
- bulk editor actions fan out into repeated CRUD calls
- bulk failure semantics are best-effort

Read model:

- chunk/window responses include placement-only static entity records
- map-wide entity list includes placements plus resolved archetype summary
- origin chunk is determined by anchor position
- overlap into neighboring chunks is computed at query time from stored geometry

### Export And Import

Map export should include referenced archetype manifests.

Import conflict rule:

- trust existing content only if full manifest hash equality matches
- fail import if manifest hashes differ

## Data Model

### Asset Version

Suggested shape:

- `id` as slug + numeric version suffix
- `uploadSlug` or temporary upload identity before binding
- source/original file metadata
- normalized runtime file metadata
- processing status
- diagnostics
- derived footprint dimensions
- derived collision dimensions
- collision class
- grounding policy
- max height delta threshold
- instancing eligibility
- category preview metadata if useful
- created/updated timestamps

### Archetype

Suggested shape:

- `id` as globally unique human-readable slug
- `name`
- `category` as controlled enum
- `tags`
- `assetVersionId`
- lifecycle state `active | deprecated | archived`
- created/updated timestamps

Controlled categories for v1:

- `building`
- `landmark`
- `industrial`
- `natural-prop`

Tags are purely organizational in v1.

### Static Entity

Suggested shape:

- `id` as human-readable ID unique within a map
- `mapId`
- `label` as optional display label
- `archetypeId`
- `position` as `{ x, z }`
- `rotation` as `{ yaw }`
- `scale`
- `yOffset`
- `state` as `active | disabled`
- `createdAt`
- `updatedAt`

Derived at runtime/editor:

- effective `y`
- oriented footprint in world space
- oriented collision box in world space
- placement validity
- overlap against chunk/window queries

## API Surface

All routes remain under the maps API domain.

V1 likely needs route groups for:

- asset upload
- asset version status and diagnostics
- asset version review/update before ready
- asset binary fetch
- archetype create/list/find/archive
- referenced archetypes for a map
- static entity CRUD
- map-wide static entity listing
- chunk responses with embedded static entities

The API should remain the source of truth for all catalog and placement data.

## Implementation Phases

### Phase 1: Contracts and persistence foundations

Status: complete on 2026-03-22.

Goal: define the three-record model and establish persistence primitives.

Changes:

- add shared contract types for:
  - `AssetVersion`
  - `Archetype`
  - `StaticEntity`
- add supporting enums for:
  - asset status
  - archetype status
  - entity state
  - controlled archetype categories
- update chunk contract to include structured `staticEntities`
- add DB tables for:
  - asset versions
  - archetypes
  - static entities
- wire static entity mutations into the shared map revision stream

Acceptance:

- contracts compile cleanly
- DB schema exists for all three record types
- chunk schema supports placement-only entity records

### Phase 2: Asset upload and processing pipeline

Status: complete on 2026-03-22.

Goal: make the API the source of truth for uploaded assets and normalized runtime artifacts.

Changes:

- add asset upload route and storage handling
- store original asset files
- add async processing pipeline for normalization
- generate normalized GLB runtime artifacts
- derive candidate footprint/collision/grounding metadata automatically
- store diagnostics and processing state
- expose asset status polling endpoints

Acceptance:

- uploaded assets move through `uploaded -> processing -> review|failed`
- normalized GLBs are stored and addressable by immutable asset version ID
- failed assets remain visible with diagnostics

### Phase 3: Asset review and archetype creation workflow

Status: complete on 2026-03-22.

Goal: let admins review derived asset metadata and promote assets into placeable archetypes.

Changes:

- add admin review flow for assets in `review`
- provide:
  - 3D preview
  - footprint overlay
  - sample terrain placement preview on synthetic terrain
  - sample terrain placement preview on real map terrain
- allow review-time corrections before ready
- require manual approval in v1
- allow:
  - asset-first workflow
  - archetype-first workflow
- prevent failed or non-ready assets from becoming placeable archetypes

Acceptance:

- admin can review and approve asset versions into `ready`
- ready asset versions become immutable
- archetypes can be created only from ready asset versions

### Phase 4: Archetype catalog and referenced-subset reads

Goal: introduce the global content catalog and resolve placements through archetypes.

Changes:

- add archetype CRUD/lifecycle routes
- add global archetype catalog reads for admin
- add referenced-subset archetype reads for gameplay and per-map admin resolution
- enforce immutable one-to-one archetype binding to asset versions
- enforce archetype statuses:
  - visible in picker by status
  - only active placeable

Acceptance:

- admin can browse global archetypes
- gameplay/admin can resolve placed entities via referenced subsets
- existing placements remain resolvable through deprecated/archived archetypes

### Phase 5: Static entity CRUD and chunk reads

Goal: persist placements and expose them through map reads using asset-derived geometry.

Changes:

- add static entity CRUD routes under maps
- add map-wide entity listing endpoint with resolved archetype summary
- add chunk query support for placement-only `staticEntities`
- compute origin chunk from anchor position
- compute overlap at query time from bound asset geometry
- implement human-readable entity ID generation with override-at-create support

Acceptance:

- entities can be created, updated, listed, and deleted
- chunk responses include placements in the correct windows
- map-wide list supports outliner use cases
- map revision increments on entity mutations

### Phase 6: Admin editor entity workflow

Goal: integrate static entity placement and management into the existing 2D editor.

Changes:

- add mixed placement/edit mode to the editor toolbar
- add global archetype catalog picker with category sections + search
- add referenced-subset resolution for existing map entities
- add entity overlays:
  - footprint
  - facing indicator
  - rotate handle
- add inspector controls for:
  - label
  - archetype
  - yaw
  - scale
  - `yOffset`
  - state
- add modifier-based snapping
- add multi-select, bulk move/state/scale, duplication, and outliner search/jump
- show disabled entities in admin only
- surface invalid placement as warning-only diagnostics

Acceptance:

- admin can place, move, rotate, duplicate, relabel, and delete entities
- bulk move/state/scale works with best-effort semantics
- invalid placements are visible and understandable in the editor

### Phase 7: Gameplay client rendering

Goal: render API-backed static entities in the gameplay client.

Changes:

- fetch referenced-subset archetype catalog for active map/session
- lazy-fetch normalized GLBs by `assetVersionId`
- add runtime cache keyed by `assetVersionId`
- render visible entities from chunk placement data
- implement hybrid rendering path:
  - scene-graph cloning baseline
  - optional instancing for eligible asset versions
- hide disabled entities in gameplay

Acceptance:

- placed entities render correctly from chunk data
- the same asset version is not redundantly reloaded
- instancing can be enabled for eligible assets without changing placement contracts

### Phase 8: Export/import support

Goal: make map exports stable against catalog drift.

Changes:

- include referenced archetype manifests in map export
- define full-manifest hash for compatibility checks
- trust existing catalog content only on exact manifest-hash match
- fail imports on incompatible collisions

Acceptance:

- exported maps carry sufficient referenced content manifests
- imports are deterministic and reject incompatible catalog conflicts

### Phase 9: Engine integration

Goal: let the Go engine consume the same static entity world model.

Changes:

- add matching engine-side records for archetype-resolved static entities
- build oriented-box spatial queries
- ingest chunk entity placements into engine indices
- expose collision/query lookups for static entities

Acceptance:

- engine can query static obstacle candidates from authored placements
- engine-side data stays aligned with API/client placement semantics

## Deferred

Explicitly deferred beyond v1:

- bridge/span-authored assets
- spline/path placement
- non-uniform scaling
- pitch/roll placement
- bulk archetype swap
- hard blocking on invalid placement
- per-map archetype allowlists
- separate content API domain
- true transactional bulk entity mutations

## Test Plan

- contract validation for all three record types
- DB and repository tests for asset versions, archetypes, and static entities
- revision tests proving entity CRUD participates in shared map revisioning
- chunk overlap tests for rotated footprints near chunk boundaries
- asset processing tests for lifecycle transitions and immutable normalized binaries
- admin workflow tests for review gating and archetype creation
- editor tests for placement, rotation, snapping, duplication, and bulk edits
- gameplay rendering tests for catalog resolution and asset-version caching
- export/import tests for manifest-hash compatibility rules

## Final Shape

The final v1 system should look like this:

- maps own placements
- the API owns the global content catalog
- asset versions own geometry/collision/grounding facts
- archetypes provide stable global placeable identities
- placements stay map-local and lightweight
- chunk reads stay placement-oriented
- clients resolve content through catalog data and immutable asset-version binaries
